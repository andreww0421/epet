# ePet 金流供應商比較與啟用門檻

文件日期：2026-11-25（Asia/Taipei）。官方資料查閱日：2026-11-24；續稿日：2026-11-25。本文是設計與決策紀錄，沒有建立商店、取得金鑰、發起交易或完成金流實作。正式選商、商務條件與稅務判斷仍未完成。

## 1. 決策範圍與目前結論

ePet 的收款主體是提供軟體訂閱的營運者；付款人是教師或小型補習班的成年購買者，訂閱對應工作區。教師是客戶，不因購買 ePet 就需要成為金流特店。本文不設計學生付款、補習班學費代收、分帳、替第三人保管款項或學生資料交換。

**先完成封閉試點的需求與付費意願證據，再決定是否實作真實金流。** 屆時以綠界 ECPay 與藍新 NewebPay 的供應商託管定期定額流程作為驗證候選；沒有完成特店核准、現行文件核實、沙盒驗收與完整報價前，不選定唯一供應商。此名單依流程適配，不是費率排名。

標記定義：**已確認**指官方公開資料支持的產品事實；**提案**指 ePet 尚未實作的行為；**待確認**指須合約、供應商回覆或測試才能結案。公開文件未寫到某能力時，標示待確認，不據此推論產品不支援。

### 3.1 ECPay：需納入適配層的已確認行為

- 定期建立流程由供應商顯示金額、週期與次數；TotalAmount 必須等於 PeriodAmount。ePet 必須先顯示一致的訂閱條件並保存同意紀錄，不能讓瀏覽器傳入價格決定實際訂單。[定期定額規格](https://developers.ecpay.com.tw/2868/)
- 第一次授權失敗不進入排程。後續授權失敗如未手動補授權，會等下一個週期；文件另列達六次失敗自動停止的規則。這不是 ePet 可自行假設的連續每日重試方案；確切失敗累計、卡片到期與終止規則須在供應商確認後寫入 adapter 契約。[定期規格](https://developers.ecpay.com.tw/2868/)、[後台管理說明](https://support.ecpay.com.tw/16214/)
- 定期作業 API 提供 ReAuth 與 Cancel，Cancel 終止後續授權；其他變更需按現行後台與開通權限處理。**官方明示 ReAuth 無法在 stage 測試。** 沙盒通過不能宣稱補授權已驗證。[定期訂單作業](https://developers.ecpay.com.tw/2900/)
- 取消後續扣款與退還既有付款是兩筆不同作業。退款需要對應每期交易；請退款 API 不會停用定期收款。[請退款](https://developers.ecpay.com.tw/2885/)、[定期授權明細查詢](https://developers.ecpay.com.tw/2892/)
- ReturnURL 是後端付款通知，OrderResultURL 是瀏覽器結果，ClientBackURL 是返回連結；名稱不能當作共用語義。另接 PeriodReturnURL 處理每期授權。結果通知須驗 CheckMacValue、成功碼及重複處理，模擬付款不能視為真實入帳。官方通知文件要求回覆 1|OK，未正確回覆會重發。[建立規格](https://developers.ecpay.com.tw/2868/)、[付款結果通知](https://developers.ecpay.com.tw/2878/)

### 3.3 TapPay：token、通知與排程責任

標準 Pay by Card Token 支援商家發起交易的標記；其 card_key／card_token 是可觸發扣款的敏感憑證，不能因不是 PAN 就放到前端、分析工具或一般日誌。選用此模式需另建安全保管、排程停止與重試限制；不在本次預設實作範圍。[Backend](https://docs.tappaysdk.com/tutorial/zh/back.html)

官方 Backend Notify 說明在未收到 HTTP 200 時按 1、2、4、8、16 分鐘重送，並建議透過 Record API 反查最新狀態。本次所讀通知段落未建立足以直接採信的簽章驗證契約；這不是斷言供應商沒有其他驗證方案。若採用，必須向供應商確認通知認證，並由持有伺服器金鑰的查詢結果核對交易，不能只信公開通知 body。[Backend Notify 與 Record API](https://docs.tappaysdk.com/tutorial/zh/back.html)

退款 API 是獨立作業；移除綁卡憑證也不等於完成退款。官方另有 Remove Card、交易歷史與對帳功能；適用收單限制須按選定服務驗證。[Backend 退款](https://docs.tappaysdk.com/tutorial/en/back.html)、[Advanced API](https://docs.tappaysdk.com/tutorial/zh/advanced.html)

## 5. 電子發票與收據責任

**付款結果、供應商交易收據與台灣統一發票是不同紀錄。** 金流合作不自動替 ePet 完成稅籍、開票、載具、作廢、折讓與保存義務。財政部《統一發票使用辦法》規定使用、免用範圍與電子發票傳輸等要求；ePet 的實際主體、銷售性質及適用方式須由營運者與會計／稅務專業者確認，不能由「教師使用教育產品」直接推論免稅或免開票。[財政部統一發票使用辦法](https://law-out.mof.gov.tw/LawContent.aspx?id=FL006084)

| 產品事實 | ePet 必須另行落地的責任 |
| --- | --- |
| 綠界有獨立 B2C 電子發票 API，官方說明亦包含買受人填統編的情況。[官方發票文件](https://developers.ecpay.com.tw/7809/) | 確認申請主體與加值中心合約；買受人統編／抬頭、適用載具／捐贈資料、開立與傳輸時點、失敗補開、退款後作廢／折讓與對帳。不要誤把信用卡扣款成功等同開票成功。 |
| ezPay 提供電子發票加值服務。[官方產品](https://inv.ezpay.com.tw/) | 藍新金流核准不視為發票服務已核准；另核實供應商、費用、API、測試與營運權限。 |
| TapPay 電子發票頁表示可選擇發票服務商並透過公版 API 整合。[官方產品](https://www.tappaysdk.com/taiwan-zhtw/service/options/e-invoice) | 確認實際開票服務商、資料流、契約與台灣稅務作業，不因「一站整合」省略核對。 |

提案：付款 ledger 與發票 ledger 分離，以內部帳期／付款識別碼關聯；各自有唯一識別碼、pending／成功／失敗狀態及補償流程。電子發票服務暫時失敗不重扣客戶信用卡；付款退款與發票作廢／折讓各自確認完成。未取得適用稅務結論與可執行作業前，不對外承諾可正式收費開票。

本案沒有選用 Merchant of Record（MoR）。日後若評估此模式，須另核對誰是銷售契約主體、台灣買受人的憑證及稅務處理、服務與退款責任；海外 MoR 提供收據或代處理部分稅務，不足以直接證明 ePet 在台灣的所有義務均已履行。

## 6. 所有供應商共用的 ePet 安全契約（提案）

1. **伺服器建立訂單。** 限獲授權的工作區購買者操作；由伺服器從版本化方案目錄決定金額、TWD、週期與權限。建立不可猜測的內部訂單／checkout 嘗試 ID，先綁定 billing account、workspace、方案版本與購買者再導轉。前端傳入的價格、角色、customer 或 workspace 不直接採信。
2. **完整導轉與最少資料。** 固定供應商允許清單、固定 HTTPS 回傳路徑與部署環境；不接受任意 return URL、表單 action、供應商 URL 或重新導向目的地。提供商家訂單識別與必要成年付款資訊，不傳學生姓名、學號、班級內容、成績或教學紀錄。PAN／CVV 不進入 ePet DOM、後端、storage、匯出或監控；不蒐集信用卡照片與客服代填資料。
3. **返回頁不授權。** 瀏覽器返回、query string、畫面成功訊息或客戶傳來的截圖僅顯示「付款確認中」。返回 state 必須短效、綁定登入者與訂單並防止重放；即使 state 合法，也不能據此授予方案權限。使用者關閉頁面仍可由後端完成確認。
4. **通知先驗證再處理。** 保留各供應商原始格式的有界輸入以執行官方 MAC／簽章或解密驗證；算法與欄位正規化固定到現行文件版本。再核對環境、MerchantID、外部交易／委託 ID、內部訂單、customer／billing account／workspace 綁定、幣別、金額、期次與成功狀態。不是每家通知都直接含 customer／workspace，缺少的欄位由伺服器既有映射及已認證查詢核實，不採信通知新增的映射。未知或偽造事件不得改權限。
5. **重送、亂序與不確定結果。** 以供應商＋環境＋交易／委託＋期次＋事件種類建立持久唯一鍵；先持久接收有效事件，再按供應商規定 ACK。重複通知不重開權限、不重開發票；亂序事件不得把已退款或已終止狀態倒退。供應商無 event ID 時，在 adapter 定義穩定去重鍵，不能只使用整包 body hash。排程與手動重試有共同排他鎖、嘗試紀錄及唯一操作 ID；交易 timeout 先查詢，不盲目重送扣款。
6. **驗證與對帳不是同一個步驟。** 無法依現行規格驗證來源或欄位不完整時，事件只進隔離佇列，由持有伺服器憑證的供應商 API 反查；再執行相同訂單綁定檢查。每日對帳漏單、失敗扣款、退款及停止委託；供應商後台人工操作也必須回寫可稽核的結果。
7. **取消與退款分離。** 取消先停止未來扣款，記錄何時向供應商請求、何時確認及下一帳期；不將本地按鈕成功冒充供應商已停用。與當期扣款競態時先查明結果，必要時按已公告政策退款。退款依原交易、金額與角色授權建立獨立操作，限制累計退款不超過實收；確認退款成功才更新相應 ledger。保留取消憑據與成人付款人通知紀錄。
8. **同意與密鑰。** 保存方案／條款版本、金額與稅別、扣款頻率、首次與後續日期、期數／到期、取消與退款方式、同意時間與成年購買者識別。金鑰僅存在伺服器 secrets，測試／正式分離，權限最小化並有輪替程序。MVP 不保存卡末四碼或其他遮罩卡資料，只保留必要供應商識別；付款 token 仍按敏感憑證保護，禁止進入一般 audit payload 與第三方分析。日後若確有顯示付款工具的需求，另作資料最小化審查。

本節是實作要求，並非聲稱目前程式或任一供應商已完成以上保護。完整託管能縮小卡資料接觸範圍，仍須由收單／供應商確認適用的 PCI DSS 與商家責任，不能宣稱因此自動免除所有要求。
